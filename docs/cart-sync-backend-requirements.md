# متطلبات الباك اند — مزامنة السلة بين الاجهزة

**التاريخ:** 2026-11-12
**الجهة المعنية:** مطورو الباك اند
**الحالة:** الواجهة الامامية **غير مكتملة** في هذا الجانب — مطلوب عمل من الطرفين
**مكمل لـ:** `docs/cart-order-backend-requirements.md`

---

## 1. المشكلة المبلّغ عنها

> «عملت طلب بالسلة من الكمبيوتر، ولما فتحت من الموبايل على نفس الحساب
> لقيت السلة فاضية.»

السلوك المتوقع من المستخدم: السلة تتبع **الحساب**، لا الجهاز.

---

## 2. التشخيص — اين الخلل بالضبط

الخلل **ليس كله في الباك اند**. المزامنة منفذة في اتجاه واحد فقط:

| الاتجاه | الحالة | المكان |
| --- | --- | --- |
| الجهاز ← الخادم (رفع) | ✅ منفذ | `postCartItemsSafe` عند الاضافة، و `syncLocalCartToServer()` عند تسجيل الدخول |
| الخادم ← الجهاز (تنزيل) | ❌ **غير منفذ** | لا يوجد اي كود يملأ سلة الموقع من `GET /user/cart` |

### تفصيل

- السلة محفوظة في `localStorage` تحت المفتاح `cart-storage`. وهذا مرتبط
  بالمتصفح والجهاز، **لا بالحساب**. لذلك الموبايل يبدأ بسلة فارغة.
- `GET /user/cart` **مستدعى فعلاً** في الموقع، لكن عبر `useCartCheckout`
  الذي يقرأ منه **كتلة `checkout` فقط** (المجاميع، التوصيل، حد الطلب).
  اما `items[]` فتُهمل بالكامل ولا تصل الى سلة العرض.
- اي ان السلة التي اضيفت من الكمبيوتر **وصلت الى الخادم**، لكن الموبايل
  لا يطلب محتواها ولا يعرضه.

> **الخلاصة:** الموقع سيُعدّل ليقرأ `items[]` من `GET /user/cart`. ولكي ينجح
> ذلك، يجب ان تكون الاستجابة كاملة وقابلة للعرض مباشرة، وان تتوفر
> الادوات المذكورة ادناه.

## 3. المطلوب — بنية `items[]` في `GET /user/cart`

يجب ان ترجع السلة عناصرها كاملة بحيث يمكن عرض جدول السلة **دون اي
مراجعة لصفحة المنتج**. حالياً الموقع يملأ هذه الحقول من صفحة المنتج وقت
الاضافة فقط، وهي تضيع عند فتح جهاز اخر.

```json
{
  "items": [
    {
      "id": 3301,
      "shop_product_variant_id": 5001,
      "product_id": 901,
      "shop_id": 12,
      "shop": { "id": 12, "name": "متجر الازياء" },
      "name": "قميص قطن",
      "image": "https://.../shirt.jpg",
      "quantity": 2,
      "note": "بدون كيس",
      "unit_price":  { "amount": 45.00, "currency": "SAR", "symbol": "ر.س", "formatted": "45.00 ر.س" },
      "line_total":  { "amount": 90.00, "currency": "SAR", "symbol": "ر.س", "formatted": "90.00 ر.س" },
      "sku": "TIK-SHIRT-BLU-M",
      "model": "MDL-2219",
      "available_quantity": 8,
      "is_instant_delivery": false,
      "category_id": 44,
      "attributes": [
        { "id": 101, "attribute": "اللون",  "value": "ازرق", "type": "color",  "hex": "#0000FF" },
        { "id": 201, "attribute": "المقاس", "value": "M",    "type": "square" }
      ],
      "extras": [ { "id": 77, "quantity": 1 } ]
    }
  ],
  "cart_type": "default",
  "checkout": { "...": "كما هو منفذ حالياً" }
}
```

### الحقول الالزامية ولماذا

| الحقل | لماذا هو الزامي |
| --- | --- |
| `id` | معرف **سطر السلة** على الخادم. تستخدمه الواجهة في `PUT` و `DELETE`. بدونه لا يمكن تعديل الكمية او الحذف من الجهاز الثاني |
| `shop_product_variant_id` | المفتاح الذي تبني عليه الواجهة هوية السطر |
| `name` و `image` | لعرض السطر. بدونهما يظهر صف فارغ |
| `unit_price` و `line_total` | **محسوبان من الخادم**. الواجهة لا تحسب السعر |
| `quantity` | الكمية المطلوبة |
| `available_quantity` | لمنع تجاوز المخزون على الجهاز الجديد |
| `is_instant_delivery` | الموقع يمنع خلط السريع مع العادي في سلة واحدة. بدونه يفشل هذا المنع بعد المزامنة |
| `cart_type` | السلة قد تكون `default` او `recipe` او `basket` او `schedule_admin_cart`. بدونه لا تعرف الواجهة نوع السلة المستعادة |
| `note` و `extras` | يجب ان تعود كما ارسلت، والا فقد المستخدم ملاحظاته واضافاته |
| `sku` و `model` و `attributes` | مطلوبة اصلاً في `docs/cart-order-backend-requirements.md` القسم 2 |

> `unit_price` و `line_total` بنفس صيغة `ApiFormattedMoney` المستخدمة في
> كتلة `checkout` (الحقول: `amount`, `currency`, `symbol`, `formatted`).
> الموقع يعرض `formatted` مباشرة.

### سلال غير اعتيادية

اذا كانت السلة من نوع `recipe` او `basket` او `schedule_admin_cart`، يجب
ان ترجع ايضاً المعرف المرتبط، والا تعذّر استكمال الطلب من الجهاز الثاني:

```json
{ "cart_type": "recipe", "recipe_id": 55 }
{ "cart_type": "basket", "admin_basket_id": 12 }
{ "cart_type": "schedule_admin_cart", "admin_schedule_basket_id": 9, "basket_schedule_id": 3 }
```

## 4. المطلوب — منع تضاعف الكميات (الاهم)

هذه النقطة **حرجة**، وقد تسبب فواتير خاطئة اذا اهملت.

### السلوك الحالي

- `POST /user/cart/items` **يجمع** الكمية على الموجود لنفس المتغير
  (هذا موثق في كود الموقع وبُني عليه).
- الموقع ينادي `syncLocalCartToServer()` عند **كل** تسجيل دخول وكل تحقق OTP.

### السيناريو الخطر

1. المستخدم يضيف قميصاً (كمية 1) من الكمبيوتر ← الخادم عنده 1.
2. يفتح الموبايل، والموقع ينزّل السلة ← صار عند الموبايل 1 محلياً.
3. المستخدم يسجل خروج ثم دخول من الموبايل.
4. `syncLocalCartToServer()` يرفع الـ 1 مجدداً ← **الخادم صار عنده 2**.

وهذا يتكرر مع كل دورة. `mergeServerCartItems` في الموقع يحمي من التكرار
**داخل الطلب الواحد فقط**، لا عبر الجلسات.

### المطلوب — احد الخيارين

**الخيار أ (المفضل): نقطة دمج صريحة ومحمية**

```http
POST /user/cart/merge
{ "items": [ { "shop_product_variant_id": 5001, "quantity": 2, "note": "..." } ] }
```

- تُستدعى **مرة واحدة فقط** عند انتقال ضيف ← مسجّل.
- دلالتها: `quantity = max(الموجود, المرسل)` وليس الجمع — فلا تتضاعف
  عند التكرار (العملية idempotent).
- ترجع السلة الكاملة بعد الدمج بنفس بنية `GET /user/cart`.

**الخيار ب: وضع صريح على النقطة الحالية**

```http
POST /user/cart/items
{ "shop_product_variant_id": 5001, "quantity": 2, "mode": "set" }
```

- `mode: "add"` (الافتراضي، السلوك الحالي) للاضافة من صفحة المنتج.
- `mode: "set"` لتثبيت الكمية بدل جمعها، تستخدمه الواجهة في المزامنة.

> ايّ الخيارين مقبول. المهم ان تتوفر **طريقة لا تجمع الكمية** حتى يصبح
> رفع السلة آمناً للتكرار. بدون ذلك لا يمكن تفعيل المزامنة بامان.

---

## 5. المطلوب — سلوك الحذف والتفريغ

| العملية | المطلوب |
| --- | --- |
| `PUT /user/cart/items/{id}` | تعديل الكمية والملاحظة لسطر واحد. مطبق حالياً، يجب ان يبقى `id` هو نفسه العائد من `GET` |
| `DELETE /user/cart/items/{id}` | حذف سطر واحد |
| `DELETE /user/cart` | **مطلوب اضافته** — تفريغ السلة كاملة. الموقع يحتاجه عند الضغط على «تفريغ السلة» ليصل الاثر للاجهزة الاخرى. حالياً التفريغ محلي فقط |

---

## 6. المطلوب — تنظيف السلة تلقائياً

لان السلة صارت تعيش على الخادم ولفترة طويلة، يجب ان تتعامل الاستجابة
مع التغيّرات التي تطرأ بين جلسة واخرى:

1. **متغير حُذف او عُطّل** — لا ترجعه كسطر عادي. اما ان يُحذف من السلة،
   او يُرجع مع `"unavailable": true` ورسالة، لتعرضها الواجهة وتمنع الطلب.
2. **كمية تجاوزت المخزون** — خفّض `quantity` الى المتوفر وأعِد
   `available_quantity` الصحيح، مع اعلام في الاستجابة.
3. **السعر تغيّر** — ارجع السعر الحالي دائماً. السلة ليست تثبيتاً للسعر.
4. **المتجر اغلق او عُطّل** — نفس معاملة البند 1.

> الواجهة ستعرض ما يصلها. المطلوب الا تصل اسطر غير قابلة للطلب بصمت،
> لان المستخدم سيصل الى الدفع ثم يُرفض طلبه دون سبب واضح.

## 7. معايير القبول

| الرقم | السيناريو | النتيجة المتوقعة |
| --- | --- | --- |
| S-01 | اضافة من الجهاز أ، ثم `GET /user/cart` من الجهاز ب | ترجع نفس الاسطر بكل الحقول المذكورة في القسم 3 |
| S-02 | تعديل الكمية من الجهاز ب | `PUT` ينجح بالـ `id` العائد من `GET`، والجهاز أ يرى التعديل بعد التحديث |
| S-03 | حذف سطر من الجهاز ب | يختفي من الجهاز أ |
| S-04 | تسجيل خروج ودخول متكرر (٣ مرات) بنفس السلة | **الكمية لا تتضاعف** ولا تتغير اطلاقاً |
| S-05 | دمج سلة ضيف فيها نفس المنتج الموجود على الخادم | الكمية تصبح `max` وليس المجموع (الخيار أ) |
| S-06 | سلة فيها ملاحظة واضافات | `note` و `extras` تعود كما ارسلت حرفياً |
| S-07 | سلة وصفة او سلة جاهزة | `cart_type` والمعرف المرتبط يعودان، ويمكن اتمام الطلب من الجهاز الثاني |
| S-08 | متغير حُذف من الداشبورد بعد اضافته للسلة | لا يظهر كسطر صالح، او يظهر معلّماً كغير متوفر |
| S-09 | منتج سريع التوصيل | `is_instant_delivery` يعود، ومنع الخلط يبقى فعالاً بعد المزامنة |
| S-10 | `DELETE /user/cart` | السلة تفرغ على كل الاجهزة |

## 8. ما سيُنفّذ في الموقع (مقابل هذا العمل)

هذه البنود **لم تُنفّذ بعد**، وتنتظر ما سبق:

- جلب `GET /user/cart` عند توفر التوكن، وملء سلة الموقع من `items[]`.
- اعتماد قاعدة واضحة للتعارض: **الخادم هو مصدر الحقيقة** للمستخدم
  المسجّل، ودمج سلة الضيف **مرة واحدة فقط** عند الانتقال من ضيف الى
  مسجّل (بدل الرفع عند كل تسجيل دخول كما يحدث الان).
- توجيه تعديل الكمية والحذف الى `PUT` و `DELETE` بمعرف السطر الخادمي.
- عرض اسطر غير المتوفر ومنع المتابعة بها.

> **ملاحظة تنسيق:** حتى تنفيذ ما سبق، تبقى السلة محلية وتبقى المشكلة
> المبلّغ عنها قائمة. البندان مترابطان، ويفضّل تسليمهما في نفس الدورة.
